### Findings

- **A Glitch deny comes before omp's prompt.** Calls 1–3 showed no omp box on the rerun, and omp's own docs
  agree (`omp://approval-mode.md`: "A deny blocks execution before a prompt"). Caveat: run 1 did not record
  which box James picked; an "Approve `bash` for this session" there would also suppress the rerun's box.
- **Calls 4 and 5 were silent allows, so they leave no Glitch line.** Re-tested after the run: both commands
  sent to Glitch's write guard exactly as Claude Code sends them (sandbox, Claude-shaped stdin) return exit 0
  with no output, and `write-guard.py` (lines 553–554) exits without logging on an allow. The box on 4 and
  5 was omp's own. Correction to an earlier draft: there is no unexplained call-5 gap.
- **The two `ask` lines are other commands**, not call 4. `touch-policy` is the guard's default label
  (`_LAST_DENY_KIND`, `write-guard.py` line 174), not a reason. Which commands they were is only in that tab's
  transcript. Still untested: a command Glitch itself pauses on (`ask`), which by the adapter code shows
  Glitch's "Glitch asks first" box and then omp's box: two boxes [inferred from `glitch.ts`, not observed].
- **The chat-answer unlock works under omp; the "yes" in this run did not qualify.** In the main omp tab a bare
  "yes" issued and used a one-time pass (`user-prompt-context-codex | prompt | OK | read-answer` at
  20:55:31Z; `read-once` state: `allow-once` then `used`). Correction to an earlier draft, which attributed
  that line to a Codex session. Here, the reply came as member turn 2, straight after the turn-1 pause, but
  was not taken as an answer: the rule (`user-prompt-context-codex.py`, `read_answer`) needs the whole
  message to be a yes phrase, and "a yes buried in a longer request" does not count.
